# Météo Midi-Pyrénées — notes techniques

## 1. Objectif

Voir la spec d'origine (fournie par l'utilisateur, non versionnée ici) : carte de Midi-Pyrénées avec prévisions 7 jours, historique météo (stations + carte de pluie), usage principal = repérer les bonnes périodes de cueillette de champignons. Usage restreint (2 utilisateurs), pas de contrainte forte de quota/scalabilité.

## 2. Comptes créés / à créer

- **Open-Meteo** : aucun compte, aucune clé.
- **Météo-France** (portail-api.meteofrance.fr) : compte créé le 09/09/2026, souscription gratuite aux API **"Données radar"** (`DonneesPubliquesRadar` v1) et **"Données d'observation"** (`DonneesPubliquesObservation`, v1 et v2 — souscrites par défaut avec le compte). Token "API Key" généré, valide 1 an (à régénérer sur le portail, section "Configurer l'API" → "Utiliser", passé cette durée), stocké dans `.env.local` (`VITE_METEOFRANCE_API_TOKEN`, non versionné). **Mise à jour 04/10/2026** : souscription ajoutée à **"Paquet Observations"** (`DonneesPubliquesPaquetObservation` v2, gratuite), et clé régénérée — **une clé "API Key" embarque la liste des API souscrites au moment de sa génération** (JWT, claim `subscribedAPIs`) : souscrire à une nouvelle API exige de régénérer la clé (portail > API > Utiliser > "Générer Token", durée de validité à régler à ~1 an, la valeur par défaut est 1 heure). Nouvelle clé valide jusqu'au **16/03/2028** ; paliers de débit lus dans le JWT : Observation 50 req/min, Paquet 100 req/min, Radar 850 req/5 min. À renouveler aussi dans le secret GitHub `METEOFRANCE_API_TOKEN` (PowerShell : `(Get-Content .env.local | Where-Object { $_ -like 'VITE_METEOFRANCE_API_TOKEN=*' }) -replace '^VITE_METEOFRANCE_API_TOKEN=','' | gh secret set METEOFRANCE_API_TOKEN`).
- **Infoclimat** (infoclimat.fr/opendata) : **pas encore créé**. Prévu par la spec pour densifier le réseau de stations (StatIC) en complément des stations officielles Météo-France — non bloquant, le module Stations fonctionne déjà bien avec les seules stations RADOME (~240 sur Midi-Pyrénées, voir 4). À créer si on veut aller plus loin : connexion/inscription gratuite sur le site, puis génération d'une clé d'API en précisant le type de réutilisation (nonÐ commercial pour cet usage).

## 3. Modules

### 3.1 Carte

Socle repris d'[Unmask](../unmask) : `MapContainer` react-leaflet, fond **Plan** (OpenStreetMap) ou **Satellite** (orthophotos IGN via `data.geopf.fr/wmts`, sans clé), sélecteur `LayersControl` en bas à gauche. Pas repris : tout le reste d'Unmask (profil altimétrique, ANFR, relief 3D) est hors sujet ici — seul le fond de carte a été copié/adapté.

Sélecteur de mode **Prévisions / Historique** (`ModeSwitch.tsx`), panneau flottant en haut à gauche.

### 3.2 Prévisions 7 jours (mode Prévisions)

Clic sur la carte → `getDailyForecast` (`lib/openMeteo.ts`), Open-Meteo `forecast`, `forecast_days=7`, **même politique « un modèle par jour » que les cartes** (AROME HD 2 jours, ARPEGE jusqu'au 4e, IFS jusqu'au 6e, AIFS le 7e ; `MODEL_DAYS`) avec `best_match` en simple repli des variables manquantes. Avant, le clic utilisait `best_match` pendant que la carte affichait AROME : à Condom le 06/10/2026 la carte montrait 21-25 mm (AROME HD à l'API : 15,8 mm) et le panneau 0,6 mm — contradiction sur un même écran. **Les modèles divergent réellement parfois** (même jour et même point : AROME 15,8 / IFS 7,2 / ARPEGE 0 mm) : chaque jour affiche son modèle (`ForecastDayCard.tsx`) et un « ⚠ modèles divergents » quand un autre modèle s'écarte d'au moins 5 mm ET d'un facteur 2. La probabilité de pluie n'est affichée que si le modèle retenu la fournit (IFS), celle de `best_match` n'ayant aucun rapport avec le cumul d'un autre modèle. Résultat affiché dans un panneau flottant en bas de l'écran (`ForecastPanel.tsx`) : icône météo (mapping WMO simplifié, `lib/weatherCode.ts`), températures min/max, cumul de pluie + probabilité, vent max, par jour. Sur mobile, un écran plein-écran (`ForecastFullscreen.tsx`) remplace ce panneau — même principe que les stations en mode Historique, voir 3.3.

**Carte de pluie prévue (recouvrement carte, jusqu'à 7 jours)** : en plus du clic ponctuel ci-dessus, un recouvrement `RainOverlay` (le même composant que la carte de pluie 24h mesurée, 3.4) affiche le cumul de pluie **prévu** par jour calendaire (Paris) sur toute la zone, avec un sélecteur de jour (`ForecastRainControls.tsx` ; « Auj. »/« Dem. » attribués d'après la DATE comparée au jour courant à Paris, pas à l'index — le maps.json peut dater de plusieurs heures ; les jours déjà écoulés sont masqués). Source : les cartes générées par `scripts/build-rain-maps.py` (voir 3.4), **un modèle par jour, le plus fin qui couvre toute la journée** : AROME HD 1,5 km (aujourd'hui et demain), ARPEGE Europe 11 km (jours 3-4), ECMWF IFS 25 km (jours 5-6), ECMWF AIFS 25 km (jour 7) — au-delà de 2 jours aucun modèle ne descend plus bas, la finesse baisse donc avec l'échéance (le panneau affiche le modèle du jour choisi). **7 jours** grâce à l'AIFS en dernier repli (l'IFS du bucket s'arrête à 144 h = 6 jours : sans AIFS la carte tombait à 5-6 jours ; les anciennes notes disaient à tort 10 jours).

### 3.3 Stations (mode Historique)

Source : API Météo-France **DonneesPubliquesObservation v2** (`public-api.meteofrance.fr/public/DPObs/v2`), pas Infoclimat pour l'instant (voir 2).

- **Liste des stations** : récupérée une fois via `/liste-stations` (CSV ~2150 stations RADOME nationales), filtrée sur l'emprise Midi-Pyrénées (`lib/config.ts`, `MIDI_PYRENEES_BOUNDS`) et figée dans `src/data/stations-midi-pyrenees.json` (239 stations) — pas un appel réseau à chaque chargement, la liste des stations ne bouge quasiment jamais. Pour la régénérer (nouvelles stations, emprise différente) : refaire l'appel `GET /public/DPObs/v2/liste-stations` avec le token, puis refiltrer sur `MIDI_PYRENEES_BOUNDS`.
- **Historique horaire + cumul quotidien (10j)** : un job GitHub Actions (`.github/workflows/station-history.yml`, 6 créneaux cron par heure + Home Assistant, voir `scripts/fetch-station-history.mjs`) accumule les observations dans `public/station-history.json` (fenêtre glissante de 10 jours). **Source : API "Paquet Observations"** (`DPPaquetObs/v2/paquet/stations/horaire?date=…`) : UN appel renvoie toutes les stations de France pour UNE heure (~1 Mo, ~2000 stations ; 236 de nos 239 présentes) — contre 239 appels avec l'API par station utilisée avant. Valeurs identiques (54 comparaisons pluie + température sur 54). **Profondeur : 23h, limite stricte côté serveur** (« date inférieure à date du jour moins 24h » -> HTTP 400). **Job auto-réparant** : le cron natif GitHub ne se déclenche qu'environ une fois sur trois (mesuré : 24 déclenchements sur 72 attendus en 6 jours ; la doc dit que `schedule` peut être retardé ou abandonné), donc chaque run re-demande TOUTES les heures des 23 dernières heures où moins de 95 % des stations ont un point (+ les 3 dernières), à 1 appel par heure — un cron sauté ne perd plus rien tant qu'un run passe au moins une fois toutes les 23h (plus long trou observé : 15h). `rr1` n'étant que la pluie de l'heure précédente, c'était la cause de pluies perdues (La Mongie le 03/10/2026 : ~2.8 mm réels, 0.8 mm affichés). Repli : si le paquet est indisponible, l'heure courante est tirée station par station. **Rattrapage profond automatique** au-delà de 23h : le même script comble station par station (API par station, ~4 jours en pratique, la doc officielle annonce 24h : non garanti), heures les plus anciennes d'abord, budget de 700 appels par run (~17 min, `DEEP_CALL_BUDGET`, surchargeable par `DEEP_BUDGET`), seulement pour les heures où moins de 95 % des stations ont un point ; timeout du job 45 min. Le workflow manuel `backfill-station-history.yml` reste pour les gros trous. ~3 stations sur 239 ne transmettent pas toutes leurs heures (jamais complètes, le message « incomplet » reste pour elles). Le navigateur lit ce fichier statique (`lib/stations.ts`, `loadHistory`), sans appeler l'API Météo-France. Champs utilisés : `rr1` (pluie de l'heure précédente, mm) et `t` (température, **en Kelvin**, converti en °C).
- **Lien Météociel** : le popup/la page station affiche un bouton « Voir la station sur Météociel » (nouvel onglet), `meteocielStationUrl` dans `lib/stations.ts` → `meteociel.fr/temps-reel/obs_villes.php?code2=<id Météo-France sans zéro initial>`. Vérifié sur Cos, Aston et Toulouse-Blagnac (31069001 aboutit à la même page que le code OMM 7630) ; pas vérifié sur les 239 stations une par une.
- **Collecte puis fusion, jamais de `git rebase` sur ce fichier** : `fetch-station-history.mjs` n'écrit que dans un fichier temporaire (`HISTORY_TMP`), et le workflow fait ensuite, à chaque tentative de push, `git reset --hard origin/master` puis `scripts/merge-station-history.mjs`. `station-history.json` tient sur UNE ligne : un rebase entre deux jobs qui le modifient (job horaire + rattrapage manuel) échouait systématiquement en conflit et faisait perdre les points de l'heure. Le rattrapage manuel utilise le même mécanisme, et les deux workflows partagent le même groupe `concurrency` (`station-history`).
- **Jours calendaires à l'heure de Paris** (pas UTC) dans le détail station (`dayKeyOfObservation`, `lib/stations.ts`) : `rr1` est la pluie de l'heure qui PRÉCÈDE l'horodatage, donc l'observation de 00:00 locale compte pour la veille. Avant, en UTC, la pluie tombée entre minuit et 2h (été) passait sur la veille et les cumuls divergeaient de Météociel. Le fichier d'historique est relu au plus toutes les 10 min (`HISTORY_MAX_AGE_MS`), et une popup desktop rouverte après 10 min se rafraîchit en silence : un onglet laissé ouvert ne reste plus figé sur les données du premier clic.
- **Secret requis** : le job utilise le secret GitHub Actions `METEOFRANCE_API_TOKEN` (à créer manuellement dans les settings du repo — jamais commité, distinct du fichier `.env.local` utilisé côté build Vite).
- **Mini prévision 5 jours** : Open-Meteo au point de la station (`getDailyForecast(point, 5)`), pas une donnée Météo-France — seul appel encore fait en direct depuis le navigateur au clic sur une station.
- Sans `public/station-history.json` peuplé (avant le premier run du job, ou si le secret n'est pas configuré), les marqueurs s'affichent quand même (liste statique) et le popup s'ouvre, mais l'historique 24h/10j reste vide (message explicite plutôt qu'un graphique vide silencieux).

### 3.4 Carte de pluie 24h (mode Historique) et cartes de prévision

#### Source actuelle — modèles Météo-France lus sur le stockage public d'Open-Meteo (depuis le 04/10/2026)

- **Pourquoi pas l'API Open-Meteo** : la règle (open-meteo.com/en/pricing et /terms) est **moins de 10 000 appels/jour (5 000/h, 600/min), usage non commercial, par IP — et chaque point d'une requête multi-lieux compte comme un appel** (poids = nb de lieux x jours/14 x variables/10, minimum 1 par lieu). L'ancienne grille (10 922 points, deux cartes, tranches de 1 821 points toutes les 2h) consommait **12 000 à 18 000 appels/jour (110 à 180 %)** et jusqu'à 44 000 si le cron avait tourné à 100 %. Aucun 429 observé (probablement des IP de runners tournantes, enforcement souple) mais la règle prévoit un blocage « sans préavis ». Les anciennes notes écartaient ce quota comme cause des 429 persistants : à tort.
- **Principe actuel** : `scripts/build-rain-maps.py` (Python : numpy, scipy, s3fs, omfiles, pillow ; versions dans `scripts/requirements-maps.txt`) lit les fichiers `.om` du bucket public `s3://openmeteo` (AWS Open Data, région us-west-2, licence CC BY 4.0, aucun quota annoncé), dossier `data_spatial/<modèle>/AAAA/MM/JJ/HH00Z/AAAA-MM-JJTHH00.om` : une grille COMPLÈTE par heure et par run, dont on ne télécharge que notre fenêtre (lecture partielle, blocs de 32x32). 7 jours de rétention. Zéro appel d'API.
- **Modèles** : AROME HD `meteofrance_arome_france_hd` (grille 0,01° ≈ 1,5 km, un run toutes les 3h, 52 pas horaires), ARPEGE Europe `meteofrance_arpege_europe` (0,1°, horaire, 102h), ECMWF `ecmwf_ifs025` (0,25°, pas de 3h puis 6h, **144 h seulement**), puis `ecmwf_aifs025_single` (AIFS, 0,25°, pas de 6h, 15 jours) — modèle d'IA d'ECMWF, utilisé uniquement pour les jours que l'IFS ne couvre pas. Chaque fichier = cumul de l'INTERVALLE (pas cumul depuis le début du run), vérifié. Grilles à lignes croissantes vers le nord (vérifié : corrélation 0,157 contre 0,014 en inversé).
- **Cumul 24h** : pour chaque heure T des 24 dernières, valeur « raccordée » comme le fait Open-Meteo pour le passé — run le plus récent précédant T avec l'échéance la plus courte (`Arome.hour`) ; somme de 24 heures (≥ 22/24 exigées, sinon le job échoue plutôt que de publier une carte biaisée).
- **Validation** : contre les pluviomètres de 228 stations pour UNE heure, le fichier S3 fait mieux que l'API (corrélation 0,44 contre 0,41 ; erreur absolue moyenne 0,46 contre 0,68 mm) ; la chaîne complète 24h sur 231 stations complètes donne une corrélation de **0,81** (pluie moyenne carte 6,03 mm, mesurée 6,29 mm). Précision : 1,5 km au lieu de 3,3 km avant.
- **Sorties** : `rain24h.png`, `forecast-day0..6.png` (niveaux de gris 8 bits, valeur = mm x 10, plafonné à 25,5 mm — le dernier palier de la légende est « 20mm+ », ligne 0 = nord, 256 x 381 cellules) et `maps.json` (emprise, dates, modèles, run, encodage, attribution). ~130 Ko au total contre 1 Mo de JSON avant.
- **Publication** : `.github/workflows/maps.yml` (6 créneaux cron par heure + Home Assistant, garde-fou d'âge de 50 min, input `force` ; `concurrency: maps`) pousse les fichiers en FORCE sur la branche orpheline **`data`** (un seul commit, jamais d'historique : des PNG qui changent à chaque run feraient sinon grossir le dépôt). Lus par l'appli sur `https://raw.githubusercontent.com/drugpad/meteochampignon/data/…` avec **jsDelivr (`cdn.jsdelivr.net/gh/drugpad/meteochampignon@data`) en secours** si raw ne répond pas (cache plus long, l'âge réel reste affiché) (`Access-Control-Allow-Origin: *`, cache 5 min ; `?v=<fetchedAt>` évite un PNG périmé à côté d'un maps.json récent). `VITE_MAPS_BASE_URL` pour pointer ailleurs en dev. `vercel.json` : `git.deploymentEnabled.data = false` (pas de déploiement par push sur `data`).
- **Tout est recalculé à chaque run** (plus de tranches ni de fusion) : un cron sauté ou un run raté retarde juste la mise à jour, il ne laisse jamais de carte incohérente — plus de carte composée de morceaux d'âges différents (les tranches entrelacées de l'ancienne version mélangeaient des fenêtres décalées jusqu'à 10h).
- **Rendu** (`RainOverlay.tsx`) : les niveaux sont agrandis x3 par lissage bilinéaire PUIS colorés avec la palette de `lib/color.ts` (contours des paliers nets), `ImageOverlay` Leaflet. Chargement paresseux : maps.json une fois, puis UNE image (celle affichée). Rechargement automatique si l'onglet redevient visible avec des cartes de plus de 20 min.
- **Attribution** (obligatoire, CC BY 4.0) : « Météo : Open-Meteo.com (CC BY 4.0), Météo-France » ajoutée au contrôle d'attribution Leaflet (`DataAttribution`, `MapView.tsx`).
- **Historique des incidents de l'ancienne architecture** (conservé pour mémoire) : cron `*/10` ignoré par GitHub (limite plateforme) ; job unique horaire avec `sleep` facturé -> dépassement du quota de 2000 min/mois du dépôt alors privé (~1560 min/jour), tous les runs bloqués (« recent account payments have failed… », visible dans les annotations du run) ; dépôt passé public le 27/09/2026 (Actions illimité et gratuit) ; trou de ~8h le 28/09 avec deux crons identiques (`5 */2`) -> minutes décalées. Les crons de minutes distinctes restent une bonne pratique.
- **Fiabilité du cron GitHub** (mesure du 28/09 au 05/10/2026) : 33 % des créneaux déclenchés au début, puis seulement ~9 % (3 déclenchements sur 34 créneaux en 17 h, trou de 8 h le 05/10), retard médian 22-25 min, jamais d'échec de run sur la période. Tout est conçu pour que ça n'ait pas d'importance : jobs auto-réparants ou intégralement recalculés, jamais « une exécution par heure obligatoire ». **Déclencheurs, du plus fiable au moins fiable** : (0) **Collecte des stations directement par Home Assistant** (`home-assistant/scripts/stations.py`, Python standard, `shell_command` à :15 et :45 ; écrit `public/station-history.json` par l'API GitHub avec le sha lu — refus 409/422 puis relecture, jamais d'écrasement ; testé contre un faux GitHub avec conflit simulé ; nécessite le jeton GitHub avec « Contents : Read and write » et `meteochampignon_mf_token` dans `secrets.yaml`) : indépendante de GitHub Actions (incident du 05/10/2026 : « The job was not acquired by Runner », run annulé après 15 min). Les traitements GitHub restent en secours. **Les cartes tournent aussi sur Home Assistant** (`home-assistant/scripts/maps.py` : lance le MÊME générateur `scripts/build-rain-maps.py`, copié par install.ps1 sous `build_rain_maps.py` ; `--launch` détaché car une commande shell HA est coupée à 60 s ; calcul à priorité basse, `MAPS_THREADS=3` ; garde-fou 50 min, verrou ; publication sur la branche `data` par l'API Git — blobs, arbre, commit SANS parent, branche mise à jour en force ; dépendances s3fs/omfiles… dans `/config/meteochampignon/pydeps` via `install_deps.py`, `--no-deps`, jamais dans le Python de HA ; `maps.json.generatedBy` dit qui a calculé ; tableau de bord = carte sur mesure `home-assistant/www/meteochampignon-card.js`, sans dépendance, déclarée comme RESSOURCE Lovelace `/local/meteochampignon-card.js?v=N` (PAS via `extra_module_url` : chargé ainsi, le module n'était parfois pas défini à temps → « Custom element doesn't exist » ; **changer le `?v=N` de la ressource à chaque nouvelle version**, /local est mis en cache longtemps) ; capteurs CPU/RAM par `sysmon.py` ; page « Détails » Mushroom/ApexCharts en repli). **Home Assistant d'abord, GitHub en secours** : HA n'appelle `workflow_dispatch` que si les données ont plus de 90 min. Testé de bout en bout contre un faux GitHub (génération réelle 197 s, 9 fichiers, création puis mise à jour forcée de la branche). (1) **Home Assistant** appelle `workflow_dispatch` toutes les 15 min (dossier `home-assistant/` : paquet YAML + tableau de bord de suivi + `install.ps1` qui copie tout sur le partage Samba et ajoute le jeton à `secrets.yaml` ; guides `docs/home-assistant.md` et `docs/github.md` ; jeton GitHub fine-grained limité à ce dépôt, Actions en lecture/écriture ; non soumis aux pertes du cron). Le paquet surveille aussi la fraîcheur des cartes/stations et alerte si retard > 3 h ou échec (voyants + notifications HA) ; (2) 6 créneaux cron par heure et par workflow (`3,13,…` cartes ; `7,17,…` stations) ; (3) lancement manuel (`gh workflow run maps.yml -f force=true` ignore le garde-fou). Garde-fous : `maps.yml` ne régénère pas si `maps.json` a moins de 50 min ; `station-history.yml` ne commit rien s'il n'y a rien de neuf ; `concurrency` sur tout.
- **Transparence côté appli** : panneaux de cartes avec « ⚠ Cartes en retard » au-delà de 6 h (`STALE_MAPS_HOURS`), détail station avec « Dernière mesure reçue : il y a X h » (alerte au-delà de 6 h).
- **Workflows épinglés** : `runs-on: ubuntu-24.04` (pas `ubuntu-latest`, qui migre vers Ubuntu 26 le 19/10/2026 : risque pour les roues binaires `omfiles`/`scipy` — relever volontairement après un essai manuel) et actions `checkout`/`setup-node`/`setup-python` en `@v6` (Node 24 ; les `@v4`/`@v5` étaient signalées comme obsolètes). Si les cartes disparaissent : l'appli affiche « Cartes de pluie indisponibles… » + « Réessayer » (messages en français, jamais l'erreur brute du navigateur) et le reste (stations, prévisions ponctuelles) continue de fonctionner ; la dernière carte publiée reste en ligne tant qu'un run ne l'a pas remplacée (le générateur échoue AVANT de publier si les données sont insuffisantes).

#### Option B — Radar Météo-France (client prêt, décodage pas branché — mise en pause, plus aucun bouton dans l'UI ; `lib/meteoFranceRadar.ts` prend la clé en PARAMÈTRE et n'est importé nulle part : ne jamais relire un token `VITE_…` dans du code navigateur, il serait embarqué dans le bundle public)

API `DonneesPubliquesRadar v1` (`lib/meteoFranceRadar.ts`), vérifiée avec un vrai token le 09/09/2026 puis re-vérifiée le 16/09/2026 :

- Zone **METROPOLE** confirmée sur `/mosaiques`.
- Observation **LAME_D_EAU** confirmée sur `/mosaiques/METROPOLE/observations` (à côté de `REFLECTIVITE`) — c'est bien le produit "lame d'eau" (cumul radar) visé par la spec.
- **Format réel identifié le 16/09/2026 (corrige une erreur des notes précédentes)** : `/produit?maille=500` et `maille=1000` renvoient tous les deux du **BUFR** gzippé (pas du HDF5, pas du GRIB) — en-tête `BUFR` confirmé après téléchargement et décompression d'un vrai fichier. Centre émetteur 85 (Toulouse), table locale version 14.
- **Panne observée** : l'endpoint `/produit` a renvoyé une erreur serveur (`303001`, `APIproductionEndpoint SUSPENDED`) pendant ~15-20 min le 16/09/2026, résolue d'elle-même — les endpoints de métadonnées (`/mosaiques`, `.../observations`) n'étaient eux pas affectés. Possible incident ponctuel côté Météo-France, à surveiller si ça se reproduit.
- **Décodage** : le format BUFR utilise des tables de descripteurs propriétaires (table locale Météo-France centre 85 v14, pas les tables OMM standard) — `pybufrkit` (pur Python) échoue sans elles. Un dépôt tiers, [theperk08/Meteo_France_Radars](https://github.com/theperk08/Meteo_France_Radars), fournit des tables locales déjà au bon format (`tables/localtabb_85_14.csv`, `localtabd_85_14.csv`) et un décodeur de référence (notebook). Pas encore testé de bout en bout dans ce projet.
- **Écueil non résolu signalé par la communauté** (forum Infoclimat) : désalignement géographique de plusieurs km entre la grille décodée et la réalité (projection Lambert conforme conique, paramètres pas clairement documentés) — personne n'a l'air d'avoir totalement résolu ça publiquement. À vérifier avant d'investir dans le reste (le décodage des valeurs ne sert à rien si le géoréférencement est faux).

**Décision du 16/09/2026** : mis en pause au profit d'un resserrage de la grille Option A (voir plus haut) — bien moins risqué, et Open-Meteo/AROME est déjà proche de la résolution native visée. Option B resterait pertinente si on veut un jour la vraie pluie mesurée (pas un modèle), mais le décodage BUFR + l'alignement géographique représentent un chantier significatif, pas encore chiffré. Si repris un jour : commencer par valider le géoréférencement sur un point connu (ex. Toulouse) avant de brancher quoi que ce soit sur la carte.

## 4. Emprise géographique

`MIDI_PYRENEES_BOUNDS` (`lib/config.ts`) : rectangle englobant lat 42.6–45.15, lon -0.4–3.4, couvrant large les 8 départements de l'ex-région (Ariège, Aveyron, Haute-Garonne, Gers, Lot, Hautes-Pyrénées, Tarn, Tarn-et-Garonne) y compris les zones frontalières (Pyrénées, causses).

## 5. Déploiement

Déployé sur Vercel (`vercel.json`, simple rewrite SPA) : https://meteochampignon.vercel.app/ — branche `master` = production. La variable Vercel `VITE_METEOFRANCE_API_TOKEN` n'est plus utilisée par l'appli (le toggle radar est supprimé) ; un token ne doit PAS être préfixé `VITE_` pour un usage navigateur (il serait embarqué dans le bundle public).
